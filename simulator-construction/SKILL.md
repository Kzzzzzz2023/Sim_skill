# 模拟器构建与抽象参考

根据目标架构、研究问题、已有工程和精度要求选择方法。以下是参考路线与设计经验，不是固定架构、逐步验收清单或性能承诺。

## 基本构建路线

通常从目标配置范围内的完整 ISA 功能建模出发，逐步加入资源、时序与系统交互：

| 构建部分 | 主要关注 | 优先考虑复用 |
| --- | --- | --- |
| ISA 与架构状态 | 指令覆盖、逐指令测试、寄存器与控制语义；功能语义尽量独立于时序组织 | 已有译码器、指令语义、浮点库、程序加载器 |
| 计算单元 | 整数、乘除、浮点、特殊与访存单元的延迟、吞吐、共享资源和输出限制 | 已验证的运算实现、适配的队列与服务组件 |
| 流水线与依赖 | 取指、译码、发射、读操作数、执行、写回；容量、相关性和回压 | 框架时间引擎、缓冲与通信机制 |
| 调度与并发 | 可发射条件、资源仲裁；GPU 的多 warp、分歧汇合、barrier 与驻留状态 | 调度接口、状态容器及可匹配的现有组件 |
| 访存路径 | LSU、地址与字节掩码、合并、局部存储、I/D-cache、缺失与返回 | 兼容的 cache、MSHR、互连及存储组件 |
| 外部存储 | 请求接受、排队、返回顺序、时钟域与背压 | 框架 memory backend、Ramulator 等外部模型 |
| 系统执行 | 线程组/CTA、kernel、host runtime；执行结束、请求排空与输出可见性 | 现有 runtime、驱动接口、加载与测试工具 |

这是依赖关系的概览，部分工作可以交叉进行。可以先用简单访存后端打通执行，再替换为 cache 和外部时序模型；不必等整机完成才测试。非 GPU 目标无需引入 warp/CTA，目标范围以外的 ISA 扩展也不必实现。


## 基础设施与框架复用

**先判断已有设施能否表达目标行为，再选择配置、适配、扩展或自建。**

Akita 将模拟引擎与硬件模型分开，提供事件推进、组件组织、通信及观测设施，并有 cache、内存与互连等组件可供选择。MGPUSim 可作为组装计算、调度和存储系统的参考，而不是新架构必须复制的模板。[框架来源](references/sources.md#框架与组件)

使用这类框架时，通常值得注意：

- **组件粒度。** 按独立状态、交互和替换需求划分组件，不必与 RTL module 一一对应。Core、cache、互连等边界可使用框架端口与消息；紧耦合的内部流水级可在一个组件内局部推进，不必每一级都创建全局事件。
- **通信与时间。** 理解发送成功、接收、重试、唤醒和同一时间戳下的事件顺序，避免把调用顺序偶然变成硬件行为。统一时间单位与时钟倍率；框架连接、适配层和硬件本身的延迟不要重复计入。
- **按语义复用。** 通用引擎和工具通常更容易复用；cache、scheduler、互连属于模型，需要核对容量、仲裁、缺失合并、重放、替换与可见性。接口相同不代表时序一致。可只复用数据阵列或队列等局部机制，而不接收整套模型假设。
- **沿用工程环境。** 以项目实际依赖版本、示例、源码和测试为准，不照搬其他版本的 API。已有框架可用时，不为套用本 Skill 而迁移或重建引擎。

外部 DRAM 模型可承担控制器与器件时序，适配层负责请求身份、接受与完成语义、时钟推进和排空。固定延时后端适合早期集成或隔离问题，但不能代表详细 DRAM 行为；接入详细后端后也不应无依据地再叠加一份固定服务延迟。[存储来源](references/sources.md#存储接口)

## 模型抽象

**保留影响竞争、接受、采样、顺序、回压和可见性的状态；优先压缩不改变这些关系的内部搬运。**

### 计算与流水线

执行单元通常可以用有限资源与完成队列表达，但延迟、启动间隔、在途容量、输出容量是不同概念。单个 `busy_until` 适合某些不可重叠资源，不足以表达可流水执行、有限在途和输出阻塞。

纯搬运 stage 可合并为延迟或最早接受时间；存在独立仲裁、容量约束、操作数采样或整体冻结的 stage 则可能需要保留。是否同拍使用刚释放的资源由目标行为决定，不由软件更新方便性决定。聚合延迟是模型参数，不应冒充 RTL 原始常数。

功能与时序可共享运算语义，由时序层控制采样和交付时刻；复用功能代码不等于在译码时提前读取所有动态操作数。也无需为不同速度模式另写一套指令方程。

### 访存与生命周期

可用父事务及子请求组织 lane 地址、掩码、部分完成和返回身份，减少 splitter、adapter 与中间寄存级的重复账本。抽象掉传输对象后，其造成的接受时机、有限带宽或返回顺序仍可能需要保留。

cache 和局部存储仍需表达目标相关的地址映射、冲突、容量、MSHR、缺失合并、refill/replay 和回压。合并请求如何计入 MSHR、是否支持广播等取决于目标，不套用其他模拟器的默认行为。执行驱动模型中的真实数据服务与可见时序也应一致，不能仅在功能内存上提前读写、再附加周期数。

请求身份应覆盖最后一个有效副作用；消费者取消、指令退休和存储服务完成不一定同步。对象复用、迟到返回、flush 和线程组重用尤其容易暴露生命周期错误。

### 抽象尺度

不同子系统可以采用不同精度。需要定位抽象误差时，可让相关后端独立替换或保留局部详细参考，不必为所有组件维护两套实现。若研究涉及流水冻结、竞争敏感同步或很小的性能差异，应重新评估当前抽象是否足够。

这些是从工程实践归纳的方法，不是等价性保证；适用边界见[经验说明](references/sources.md#工程经验)。

## 调试与精度参考

功能问题通常先于周期校准处理，性能测量再以已知正确工作量为基础。可采用开发—测试反馈逐步收敛，具体轮次、测试粒度和停止条件由任务决定。

有 RTL 或可信参考时，可比较 issue、accept、service、miss、fill、response、writeback 等关键事件，寻找**能够解释后续偏差的最早差异**。先排查容量、仲裁、接受时机、采样和释放关系，再考虑聚合参数。不同抽象层未必能逐拍一一对齐，比较共同可见边界通常更有意义。

没有逐拍参考时，可用依赖链、独立指令流、bank 冲突、缺失合并、输出阻塞等小程序检查延迟与吞吐关系；结合占用率、停顿原因和硬件测量判断。最差 benchmark 可作为线索，但不宜用名称分支或专属周期乘数修补模型。

对 Akita Smart Ticking 等按需推进机制，挂起或提前结束时应检查进展判定与唤醒来源：消息到达、端口释放、内部到期事件或条件等待是否还会触发工作。没有退休指令不等于系统静止。[推进机制来源](references/sources.md#推进与观测)

评估时分开看功能结果、周期误差和宿主耗时，并关注误差尾部、未用于调参的输入及资源变化趋势。平均误差小不意味着每项可靠；时间影响控制流的程序需要单独解释。详细模型本身也需验证，不自动等于 RTL 真值。

## 实现性能参考

先区分**减少需要模拟的工作**与**让同样的模拟工作执行得更便宜**。结构抽象可能改变周期预测；纯实现优化则应保持原模型行为。在确定性、同输入条件下，可对照输出、周期/指令计数及关键事件，只有总周期相同仍不足以证明等价。

热点分析后可考虑减少重复状态复制、临时分配、无用报告、重复查询与跨语言调用。小而有界的数组或扫描可能比活动集合、复杂池化更合适；借用视图与缓存需要明确有效期，软件存储池大小不应意外增加新的硬件回压。

门控和批处理的前提是不会遗漏定时完成、控制唤醒或外部模型的维护事件。Smart Ticking、全局跳时和减少跨语言调用不是同一件事；批量调用仍可能需要执行每个逻辑时钟，不能仅因当前没有请求就跳过 DRAM 推进。

用相同输入、同类宿主资源和明确构建配置做重复配对测量，区分启动、模拟区间与完整进程耗时。诊断计数与 profile 用于解释，不直接换算加速比。PGO、GC、线程数和绑定策略由实测决定，保留负结果，不照搬其他机器或规模的最优值。
