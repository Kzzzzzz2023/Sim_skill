# 调试与性能

## 用现象定位边界

| 现象 | 可优先检查 |
| --- | --- |
| 构建、加载或调用失败 | 本地依赖是否完整、接口版本、库路径、构建入口与并发约定 |
| 输出错误但单条指令测试通过 | 动态值采样、字段写回、真实访存数据、部分完成、身份重用和同步 |
| 事件队列耗尽但任务未结束 | 首次事件、消息与端口通知、内部到期、条件等待和进展判定 |
| 长期运行但没有有效推进 | 同一请求反复重试、未释放额度、循环等待、无效 Tick 或重复 flush |
| 功能正确但周期不符 | 计数范围、供给与接受、仲裁、容量、返回顺序和释放边界 |
| 周期接近但宿主执行很慢 | 每拍软件工作、分配复制、报告生成、运行入口与跨语言调用 |

开发与测试按问题交替进行，已有正确部分不必重做。先区分环境、语义、时序与实现成本，不通过调整周期掩盖功能问题，也不以环境失败判断模型错误。

## 利用共同边界定位时序

统一输入、配置、初始化状态、时间单位和计数起止，再比较共同可见事件。创建、进入队列、实际接受、服务、返回和消费可能处于不同边界；同名计数也未必覆盖同一窗口。复位前未初始化事件、启动开销与输出 flush 是否计入，都应先核对。

寻找能够解释后续偏差的最早差异，不机械寻找两份日志第一行不同。将身份、候选资格、选择、实际接受、占用和释放一起观察：选中了未必被接受，结果到期未必能写回。不同抽象层只在共同边界对齐，不要求内部 stage 一一对应。

可先以少量事件缩小到组件，再查看该组件的输入、队列和停顿原因；无需默认输出所有状态。依赖链和独立指令流可区分延迟与吞吐，饱和队列、输出阻塞、bank 冲突、同 line 缺失与部分返回可区分资源假设。多上下文重用、延迟控制反馈和重复启动有助于检查生命周期。

没有逐拍参考时，用上述小程序、局部占用、参数扰动和允许的硬件测量形成证据。最差或大规模用例可暴露问题，但不按名称选择模型、添加专属周期乘数或用参考输出替换实际执行。先修复竞争、采样和顺序，再考虑聚合延迟。

一次只改变可解释的一组机制通常便于定位；保留可复现输入和受影响路径的测试即可，不要求固定的调试仪式。参数变化方向是诊断线索，不是所有资源变化都必须满足简单单调关系；反常方向应解释其竞争和调度原因。

## 区分三种收益

**模型抽象**减少需要模拟的内部动作，可能改变周期预测，需要重新评估功能、时序和适用范围。**纯实现优化**让原模型执行得更便宜，在确定性、同输入条件下应保持结果、计数和相关事件。**编译及宿主配置**改变运行成本，不应改变目标硬件资源。

只有总周期相同不足以证明行为相同，也不能把少模拟的周期全部算成每拍代码变快。模型修正后建立新的自身比较基线；后续实现优化与该基线对照，而非强行匹配另一抽象层的内部日志。

## 减少重复工作

先用本地热点分析和计数判断主要成本，不固定优化次序。以下方法只在相应工作确实重复、且语义边界不受影响时考虑。

| 主要成本 | 可考虑的方法 | 容易遗漏的条件 |
| --- | --- | --- |
| 每拍构造完整报告、资源清单或状态快照 | 查询实际 owner，观测按需生成 | 观察数据不成为推进依据；公开快照不别名内部存储 |
| 层层复制动态指令或事务 | 共享主体记录、紧凑值或稳定引用 | 采样时刻、字段写回与引用寿命仍清楚 |
| 重复创建短命数组、消息或返回容器 | 复用有界存储、调用者提供输出区 | 软件池不引入新硬件回压；错误或空输出不残留旧有效位 |
| 同一状态重复仲裁、查询和组装响应 | 缓存稳定求值区间内的结果 | 状态改变后失效，不只用时间戳判断 |
| 无需求却反复准备控制上下文 | 按实际语义事件采样必要字段 | 条件等待、计时事件与有副作用的回调不能省略 |
| 每拍重新进入运行接口或扫描全部生命周期 | 复用运行作用域、回调与未变化的关联 | 预算、取消、错误和真正的控制边界仍响应 |

状态空间小且有界时，线性扫描可能比活动集合或复杂索引更便宜；使用何种结构由规模与实测决定。缓存查询保留可校验的身份和代次，不能让缓存成为与主体账本冲突的第二真值。

同步借用只在约定调用内有效，跨拍或跨回调保留的数据需要独立存储或稳定所有者。同一时间戳也可能已有多次服务和接纳，因此较宽缓存并不天然安全。外部回调可能重入时，尤其要检查借用期内是否允许状态变化。

## 门控、批量与时间

局部门控省掉无作用的求值；事件推进减少不必调用的周期；跨语言批量减少边界往返。三者不是同一种优化。没有普通指令、请求或退休，仍可能有定时完成、同步等待、服务尾部或维护事件。

跨语言调用昂贵时，可在后端允许的区间合并调用；若后端没有安全跳时能力，内部仍执行每个逻辑时钟和必要的返回轮询。批量边界需考虑新请求、待返回事件、关闭排空及错误上报；延后轮询可能改变接受或可见时刻。

若采用下一事件跳时，要覆盖所有相关时钟域、到期工作和维护事件，并按经过时间更新计数。组件局部静止不能推出全局静止。用非空事务与边界测试检查批量，空轨迹相等没有证明力；未能观测的内部事件不宣称已逐拍验证。

## 评估与保留方案

功能、周期误差和宿主耗时分别看。平均误差之外保留尾部、未参与调参的输入、规模变化及资源趋势；时间影响控制流的程序单独解释工作量和失败，不混入普通等工作量测速。更细的模型也不是自动正确的真值。

正式速度使用明确代码、库、输入和环境的重复配对测量，区分启动、模拟区间与完整进程。profile、race 和详细插桩构建不作为生产速度证据；累计 CPU 占比、少一次分配或调用次数下降不能直接换算耗时收益。

软件循环数、硬件周期和各时钟域计数可能不同；每拍成本的分母要明确。累计分配、结束时堆大小与峰值内存也不是同一指标，跨语言运行还可能遗漏原生分配。

线程数、垃圾回收、绑定与编译配置只在任务允许范围内实测。小输入的初始化占比与长输入稳态成本不同，局部更快也可能使端到端退化；保留负结果，没有稳定收益即可撤回。不同阶段或相互重叠的加速数字不拼接成总贡献。

当功能或精度退化时再返回对应问题；任务目标已满足时无需强制继续优化。测试规模、检查力度和是否采用更细参考，由当前任务和剩余不确定性决定。
